# ADR-002: Monetary amounts stored as integer fils (BigInt), not decimals or floats

**Date:** 2026-08-23
**Status:** ACCEPTED
**Task Reference:** T-003
**Reversibility:** LOW

## Context
All financial figures (LPO values, PC gross/retention/net, budgets, VO values) must sum exactly; source reports reconcile totals "to the fils" (e.g., cumulative certified AED 9,376,871.62 matched PC13's stated total). Currency is assumed AED-only (PRD OQ-1 open). JavaScript `number` loses integer precision above 2^53 fils (~AED 90 trillion — safe here) but float arithmetic on decimal fractions is not exact; Prisma `Decimal` serializes to string and complicates JSON/chart layers.

## Options Considered
1. **BigInt fils** — store minor units as integers; convert at boundaries only.
2. **Prisma Decimal(18,2)** — exact in DB, string-typed in JS, needs decimal library for math.
3. **Float/number AED** — simplest ergonomics; rejected outright: rounding drift in sums/reconciliation.

## Decision
Option 1. Zod transforms accept human decimal strings at the API edge; SQL `SUM(bigint)` stays exact; charts convert to number at render time. Fils precision exceeds the reports' own 2-dp fidelity.

## Consequences
+ Exact arithmetic everywhere; trivially testable; no decimal library dependency.
− Every read/write passes through money helpers (`lib/money.ts`) — convention must be enforced in review/tests.
− If multi-currency arrives (OQ-1), scale-per-currency must be added to the model; schema change would be required (hence LOW reversibility).
